# 설명 유형과 구성

아래 구분은 집필 관점이며 새 Frontmatter type 목록이 아니다. 실제 저장 가능한 값은 프로젝트 docs/HMY_DOCUMENT_TYPES.md에서 확인한다.

| 유형 | 설명의 중심 | 피할 구성 |
| --- | --- | --- |
| 개념·원리 | 정의→구성 요소→작동→실제 영향 | 정의와 링크만 제시 |
| 기술 규격 | 계층·세대·선택 기능·호환 조건 | 커넥터 모양을 기능으로 단정 |
| 하드웨어 부품 | 역할·구조·부품 간 관계 | 사양표 복사 |
| 제품·플랫폼 | 모델·리비전·지원 조건 | 특성을 회사 전체로 확대 |
| 비교 | 같은 조건의 차이와 선택 조건 | 다른 시험 결과의 순위화 |
| 트러블슈팅 | 관찰→가설→확인→분기 | 증상 하나로 불량 확정 |
| 작업 가이드 | 준비·순서·정상 결과·실패 조치 | 개념에 단계 번호 부여 |
| 기업·브랜드 | 기업 개요·사업·이력·관계 | 일반 설치·케이블 설명 |
| 역사·연표 | 시점·기술 변화·산업 맥락 | 날짜 목록만 제시 |
| 생태계 | 참여자 유형·관계·국내 접점 | 대표 회사 몇 곳만 나열 |
| 허브 | 분야 구조·학습 경로·문제별 이동 | 링크만 모음 |

목적에 필요한 절만 쓴다. type 없는 기존 개념·허브에 정보표를 일괄 추가하지 않는다. 소프트웨어 진단 도구는 측정 대상·버전·결과와 해석 한계를 설명한다. 다른 문서의 본론은 문맥에 필요한 설명을 유지하고 연결한다. GPU 칩과 그래픽카드처럼 다른 범위를 자동 병합하지 않는다.

유형은 시각화를 강제하지 않는다. 구조·데이터 경로에는 기존 도식이나 관계 diagram, 비교에는 같은 조건의 표/plot, 입력 관계에는 지원되는 explorer를 검토한다. 캐시·채널·전원은 개념도와 실물/실측을 구분한다. 절차와 진단은 단계 진행과 관찰별 분기를 구별한다. [형식 선택](visual-explanations.md)을 필요한 경우에만 읽고 Light Edit의 범위를 확대하지 않는다.
