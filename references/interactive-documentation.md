# 인터랙티브 설명 작성

인터랙션은 변수·연결·관찰의 차이를 독자가 탐색하는 도구다. 글의 기본 설명과 안전 조건을 대신하지 않는다. 제공 기능은 사용 프로젝트의 공통 모델·renderer·DOM enhancer와 Obsidian 편집 구현을 함께 확인한다. 계획 문서와 테스트 파일만 존재하는 기능은 지원으로 소개하지 않는다.

## 작성 계약

| 요소 | 담을 내용 |
| --- | --- |
| 고정 사실 | 변수를 바꿔도 유지되는 기술 관계 |
| 입력 변수 | 이름·단위·기본값·허용 범위 |
| 관계 | 실제 구현된 계산식 또는 노드 연결 |
| 출력 | 계산 결과·단위·선택 경로와 의미 |
| 한계 | 생략한 조건, 실측/이론 구분, 적용 대상 |
| 기본 설명 | 조작 전과 JavaScript 없이도 읽을 핵심 내용 |

새로운 JavaScript나 계산 expression을 Markdown에 넣지 않는다. 기존 hmy-explorer가 구현한 kind와 baseline만 사용한다. 문서마다 계산기 앱을 만들거나 엔진·플러그인을 수정하는 작업은 집필 스킬의 역할 밖이다. 소스 접근이 없으면 제공된 스냅샷의 확인 범위를 밝히고 정적 공식·계산 예를 작성한다.

## 진단

hmy-diagnosis는 steps의 id, text/title, yes/no 또는 choices, detail, action을 확인한다. 분기가 있는 단계에는 고유 ID를 주고 모든 target이 실제 단계에 존재하는지 검사한다. 한 단계에서 choices와 yes/no를 섞지 않고 순환 경로를 만들지 않는다. 구문 검사뿐 아니라 실제 Obsidian 저장 validation을 호출한다.

첫 단계는 관찰과 연결·데이터 조건에서 출발한다. 선택지가 실제로 알려지지 않은 시험 결과를 대신하지 않게 한다. 증상 하나로 불량을 확정하지 않는다. 전원 분리·데이터 보존·위험 작업 중단 조건은 관련 조치 가까이와 블록 밖 본문에도 쓴다. 사용자가 아직 선택하지 않은 경로에서도 안전 조건을 읽을 수 있어야 한다.

현재 enhancer가 연결되면 선택·이전·처음·전체 흐름 같은 조작이 가능하다. 기존 원문·플랫폼에 따라 정적 경로가 남을 수 있으며, 조작 결과는 원인을 자동 판정한 결과가 아니다. 없는 ID를 옛 parser가 받아들이더라도 저장·작성 완료로 보지 않는다.

## 플랫폼 확인

- parser: 모델이 만들어지고 잘못된 입력이 거절되는가?
- renderer: 본문·공식·단위·전체 경로·기본 표가 출력되는가?
- enhancer: 입력 변경·선택·초기화·오류 상태가 실제로 동작하는가?
- Obsidian: 원문 unknown field를 버리지 않고 읽기·Live Preview·편집·저장·Undo가 가능한가?
- Quartz: 최신 로컬 build에 자원이 포함되고 직접 URL·SPA 재방문에서 동작하는가?

키보드 초점·모바일 폭·라이트/다크·no-JS·인쇄를 확인한다. 이미지 비교 슬라이더는 양쪽 로드와 같은 종횡비를 충족할 때만 나타날 수 있다. 이미지 원본과 권리 설명이 남는 정적 비교는 실패가 아니다. guide 진행이나 timeline 검색도 실제 enhancer가 있을 때만 안내하며 version 필드를 문서 전환 기능으로 설명하지 않는다.

native 함수 검사와 공통 DOM 확인은 실제 Obsidian 앱 확인과 다르다. 도구가 없어 실행하지 않은 단계는 Not run이다. 지원이 다른 경우 독자용 정적 설명을 보존하고 구체적 차이는 작업 보고에 남긴다.
